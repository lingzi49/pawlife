# PawLife 项目案例：从宠物健康记录到可演示的产品原型

> 本文用于作品集、简历项目介绍和面试准备。内容基于当前仓库代码、README、技术文档和 Showcase 的实际状态整理；没有使用虚构的用户调研数据或商业指标。

---

## 1. 项目概述

**PawLife 是一个面向宠物主人的健康管理与日常照护 Web 应用原型。**

它以宠物档案为基础，把健康事件、饮食参考、体重与体况、照护提醒、照片记录和轻量成长激励组织在同一个产品链路中。目标用户是希望系统记录狗狗日常健康信息、但缺少专业工具或照护经验的新手养犬人。

产品价值不在于替代兽医，而在于：

- 把分散的疫苗、驱虫、洗澡、体重和异常观察整理成连续档案；
- 用规则生成可解释的饮食、保健品和提醒参考；
- 通过记录、提醒和轻度激励，帮助主人维持长期照护习惯；
- 在出现高风险描述时，优先提示就医并暂停当天的建议展示。

当前项目包含三个独立部分：

| 部分 | 定位 |
| --- | --- |
| 原始 Web 应用 | Python + FastAPI + SQLite，单文件全栈原型，是主要业务实现 |
| `showcase/` | 独立静态演示版，使用模拟宠物「团团」和 `localStorage` |
| `miniprogram/` | 独立微信小程序及后端，尚未完成端到端验证 |

三者不共享数据库、用户体系或完整业务运行时。Showcase 用于公开演示页面和主要交互，不代表原始 Web 应用已经具备全部同名能力。

## 2. 用户问题与产品机会

以下内容是产品设计和场景分析，不是正式用户调研结论；仓库中没有访谈人数、问卷样本或市场数据。

### 2.1 信息分散

宠物健康信息通常散落在聊天记录、纸质疫苗本、相册、备忘录和临时记忆里。主人真正需要时，往往很难快速回答：

- 上次驱虫是什么时候？
- 最近一次体重变化是否异常？
- 狗狗之前是否出现过类似症状？
- 过敏源和已知疾病有没有影响当前饮食？

### 2.2 记录难以持续

单次记录并不难，难的是持续记录并在之后复用。没有反馈、提醒和可回看的趋势，记录很容易中断。

### 2.3 建议缺少可解释性

饮食、保健品和护理建议如果只给结论，用户很难判断依据。PawLife 的选择是把计算依据、档案字段和规则条件展示出来，同时明确这些结果是参考而不是诊断。

### 2.4 产品机会

将“档案 → 记录 → 计算/提醒 → 回看与激励”连成一条可执行路径，而不是只做一个信息展示页。这个判断来自对养宠日常场景的拆解，不是来自已完成的用户研究。

## 3. 产品设计与核心功能

### 3.1 宠物档案

档案是系统的核心数据对象，记录名字、品种、生日、体重、性别、绝育状态、过敏源、已知疾病、到家日期和洗澡间隔。

设计要点：

- 档案不是展示信息，而是饮食、保健品、提醒和勋章计算的输入；
- 体重变化会同步体重记录；
- 过敏源和疾病会影响食材筛选和保健品方向；
- 当前 Web 端只支持“最新创建的一只狗狗”，没有多宠物切换。

### 3.2 健康事件与时间线

事件类型包括疫苗、驱虫、发情、异常行为、洗澡和每日检查。用户可以记录日期和详情，在时间线中筛选、查看、编辑、删除和上传照片。

事件不是孤立记录：它会触发风险扫描、提醒更新、勋章检查和派生状态重算。

### 3.3 高风险提示与建议暂停

异常行为表单支持症状多选和补充描述。前后端使用同一套高风险词表及同义表达进行扫描。

设计时特意处理了三个容易出错的场景：

- **否定表达**：“没有持续呕吐”不应触发急诊提示；
- **历史描述**：“上次持续呕吐，今天已经恢复”不应被当成当天急症；
- **多条风险并存**：删除或编辑其中一条风险事件时，不能错误解除其他事件造成的暂停。

高风险记录会暂停当天饮食和保健品建议，用户联系兽医后可手动恢复。风险提示是关键词规则，不是诊断，也不覆盖所有急症。

### 3.4 饮食与过敏过滤

饮食模块根据体重、年龄阶段、绝育状态和性别计算 RER/DER，再换算每日克数和每餐克数；根据年龄和体型选择食材组合，并按过敏源替换蛋白质、蔬菜和碳水。

这里的产品判断是：

- 把计算依据展示出来，让用户知道结果从哪里来；
- 对过敏源做过滤和兜底，而不是只显示“建议咨询兽医”；
- 明确 1.5 kcal/g、宏量配比和食材营养表是项目参数，不是临床处方；
- 不把未计算的钙磷比包装成已完成的能力。

### 3.5 保健品、提醒与成长记录

- **保健品**：基础规则读取品种、年龄、体重、性别、绝育状态、异常行为历史和疾病，按合并键去重；
- **提醒**：疫苗、驱虫、发情、洗澡、体重、体况和每日检查在应用内展示；疫苗周期由可配置参数统一提供；
- **成长记录**：签到、爪印、任务、勋章、每日测验和健康照片构成轻量反馈层。

这些模块服务于“持续使用”，不改变健康建议的医学含义。

### 3.6 Showcase 演示层

`showcase/` 是独立静态演示版：

- 7 个页面，页面结构和主要入口与原始 Web 应用基本一致；
- 使用模拟宠物「团团」和浏览器 `localStorage`；
- 不调用后端 API，不读写 SQLite；
- 手机和桌面端都可直接静态访问，并兼容 GitHub Pages 项目子路径；
- 在线演示：<https://lingzi49.github.io/pawlife/>（2026-11-16 实测可访问）；
- 演示版中的任务卡、体重范围和部分交互与原始 Web 应用存在差异，不能作为原始应用能力的完整证明。

## 4. 关键业务逻辑设计

### 4.1 档案作为单一输入源

饮食、保健品、提醒和勋章都从同一份档案读取数据。这样能避免每个页面各自维护一套档案字段，也便于解释“为什么给出这个建议”。

### 4.2 原始事件与派生状态分离

健康事件是原始记录；洗澡日期、风险暂停、健康相册元数据是派生状态。

设计原则：

- 编辑或删除洗澡事件后，重新计算最近洗澡日期；
- 编辑异常事件后，重新扫描风险并更新风险标记；
- 删除事件时，清理照片文件和健康相册引用；
- 勋章和爪印按成就记录保留，不因删除事件回滚；
- `risk_logs` 作为历史审计记录保留，不随编辑/删除重写。

这避免了“原始记录已删除，但派生状态仍指向旧数据”的常见问题。

### 4.3 风险识别的边界处理

高风险识别使用关键词和同义表达，但增加了上下文判断：

- 关键词前出现“没有、未见、无明显”等否定词时跳过；
- 历史事件同时出现“今天已经恢复/现在正常”等恢复描述时跳过；
- 同一文本中后续未否定的风险词仍然命中；
- 服务端独立扫描，不依赖前端是否传 `high_risk`。

这仍然不是医学模型，无法覆盖所有表述；其价值是降低明显误报，同时让风险提示在真实页面中可达。

### 4.4 可配置的提醒参数

疫苗提醒周期使用服务端参数 `VACCINE_REMINDER_DAYS`，默认 1095 天，通过 `/api/health_check` 返回给前端。

设计没有把 1095 天定义成所有疫苗的医学标准，而是把它作为项目提醒参数；不同疫苗的免疫计划应由兽医决定。

### 4.5 过敏过滤的可解释性

过敏源会映射到食材集合，再用于替换食谱和过滤替换选项。极端情况下如果所有候选都被排除，系统会回退到第一个候选，这个边界本身也记录了风险：它不能保证一定安全。

## 5. AI 辅助开发与人工判断

项目开发过程中使用 AI 工具辅助需求整理、代码生成、调试和文档整理，但运行时不是 AI 诊断系统：饮食、保健品、提醒、勋章和风险提示都由本地 Python/JavaScript 规则和结构化数据计算。

AI 在项目中的实际作用：

- 协助把 PRD、数据模型和业务规则拆成可实现的模块；
- 辅助生成页面、接口和规则实现；
- 辅助定位前后端不一致、死代码和文档漂移；
- 辅助编写回归测试和浏览器验证脚本；
- 辅助整理 README、技术细节和审计报告。

人工判断负责：

- 决定产品边界：这是一个参考工具，不是兽医诊断系统；
- 判断哪些问题值得修、哪些需要更大架构调整而暂缓；
- 核对风险提示、饮食参数和医学相关文案；
- 审查 AI 生成代码的正确性和安全边界；
- 决定不虚构用户数据、测试结果和部署状态。

这部分是项目中最能体现产品和工程判断的地方：不是“用了 AI”，而是用 AI 加速实现，同时用规则、测试和文档约束结果。

## 7. 反思与后续规划

### 当前限制

- Web 端单用户、单宠物，没有认证和数据隔离；
- CORS 已默认收紧，但不能替代认证和访问控制；
- 健康规则和食材数据没有经过完整兽医审核；
- 微信小程序与 Web 应用不共享数据，端到端链路未验证；
- 头像盲盒管理入口、签到里程碑统计口径等仍有未完成部分；
- 自动化测试只覆盖部分规则和页面流程。

### 后续优先级

1. **公开演示**：保持只部署 `showcase/`，不公开运行原始 Web 后端；维护当前 GitHub Pages 静态站点。
2. **产品可信度**：由兽医专业人员审核高风险词、同义表达、饮食参数和保健品规则；明确所有健康内容的参考边界。
3. **安全与数据**：在公网场景增加认证、权限、HTTPS、数据隔离和备份恢复；不把当前单用户原型直接暴露给真实用户。
4. **工程化**：补充 API、数据库和浏览器回归测试；评估外键和版本化迁移；统一错误响应和勋章数据结构。
5. **多端能力**：继续独立验证小程序链路，明确与 Web 应用的数据边界，不强行合并成一套未验证的统一系统。

## 8. 面试讲述要点

可以按以下顺序讲这个项目：

1. **问题**：宠物健康信息分散、记录难持续、建议缺少依据。
2. **定位**：不是 AI 诊断，而是档案驱动的健康管理原型。
3. **设计**：档案作为输入源；事件产生派生状态；风险提示优先就医；饮食/提醒可解释。
4. **实现**：FastAPI + SQLite 单文件原型，独立静态 Showcase，小程序独立子项目。
5. **判断**：哪些问题修、哪些列为后续；如何处理否定/历史症状、多风险并存和手动恢复。
6. **验证**：规则测试、浏览器回归、子路径验证；同时明确测试和医学验证的边界。
7. **反思**：认证、多用户、真实数据隔离和专业审核仍是下一阶段工作；静态 Showcase 已部署。
